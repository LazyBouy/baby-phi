## Plan vs. reality
- **Plan said** (plan-archive line 1159, §P2 Deliverables + §C6 + §G5): 9 session-tier repo methods described as "persist / append" without specifying CRUD verb. Implicit convention from M3/M4 `upsert_*` helpers (`UPDATE type::thing('<table>', $id) CONTENT $body` as create-or-update idiom).
- **Reality (shipped state at current HEAD)**: `persist_session` uses `CREATE type::thing('session', $id) CONTENT $body RETURN NONE` ([`repo_impl.rs:2238`](../../../../../../modules/crates/store/src/repo_impl.rs#L2238)) — mapping SurrealDB's unique-violation error to `RepositoryError::Conflict`. `append_loop_record` + `append_turn` also use `CREATE` (fresh ids so CREATE never conflicts). Discovery driver: UPDATE-as-upsert silently writes nothing on non-existent records with SCHEMAFULL + FLEXIBLE fields.
- **Root cause**: `reality-feedback-contradicted-estimate` (SurrealDB DDL semantics contradicted the plan's implicit UPDATE-as-upsert assumption).
